01 · goalwhat & why

现有 review agent 只在交易之后被触发（挂在 transaction detail 抽屉里）。它读单一时间框架的 ±100 根 K 线，做事后复盘。缺口很明显：真正影响结果的思考发生在下单之前。

current state
复盘型 agent，只在交易后可用
  • 入口挂在 TransactionDetail
  • context = 单个 timeframe 的 ±100 根 K 线
  • 依赖已存在的 transactions 行
  • 无法为「还没下单的想法」保留讨论历史
desired state
决策型 agent，专为交易前一致性检查
  • 侧栏一级入口 /pre-trade
  • context = 多时间框架 K 线 + 标注主交易 tf
  • 每根 tf 的 candle 数可调（默认 100）
  • 不需要先建 transaction，独立持久化讨论草稿

先复述一下我看到的：主交易框架 4H，方向 long， 在 63.8k 支撑做多，止损 62.5k，目标 68k。R:R ≈ 3.2。

值得肯定的地方

  • 入场依附结构位而不是追高，方向和 1D neckline 对齐
  • R:R > 3，符合你的账号历史盈亏比中位数

没考虑到的点

  • 1D neckline 的定义是 63500 还是 64100？两个价位差 1%，直接影响你现在这单是「回踩确认」还是「击穿反抽」
  • 15M 缺失还没到你要的支撑，为什么已经想 long？可能是你把 4H 的 sweep 当成了短周期确认
我的建议：把 stop 移到 62.2k（1D 上一波低点下面 30 bps），或者把 size 减一半、等 15M 出现明确 reclaim 再加仓。

05 · data model · pick onehow to persist a pre-trade discussion

dimension
option a · new table + shared conversationsrecommended
option b · discriminator column
what changes
  • new table pre_trades
  • relax conversations.transactionId → nullable
  • add conversations.preTradeId (nullable fk)
  • check constraint: exactly one of the two ids present
  • add kind col to conversations
  • store pre-trade fields (pair / primary tf / tfs json / idea) directly on conversations row
  • polymorphic table
query shape
  • parallel to today's getConversationByTransaction
  • clean joins: pre_trades ⨝ conversations ⨝ messages
  • every query needs a where kind = ?
  • columns unused half the time (weak invariant)
extensibility
  • later "convert to transaction" = simple fk hop
  • can list drafts independently of transactions
  • adding new agent kinds keeps widening the table
  • hard to migrate away later
migration cost
  • one migration: create table + alter nullable + add fk column
  • reversible, no data change
  • alter conversations wide
  • backfill kind='review' on all existing rows

pre_trades proposed columns: id · userId · tradingPair · direction? · primaryTimeFrame · timeframesJson (`[{tf, candleCount}]`) · anchorMs · idea · providerId? · status · createdAt · updatedAt.

10 · risks & failure modeswhat could go wrong

payload bloat
5 tf × 500 candles ≈ 40kb → 上下文吃紧
  • 维持 12k char cap，按 context-first 顺序降级
  • setup 底部实时显示 payload size
provider drift
锁 provider 才能保证长对话一致
  • 复用 review 的 lockedProviderId pattern
  • 一旦第一条 assistant 回复完成即锁定
coinank rate limit
一次点击 5 个 tf 并发拉取
  • 用 Promise.allSettled，单 tf 失败降级不阻断
  • 失败 tf 在 payload 里显式注明"unavailable"
nullable transactionId
历史数据兼容 · migration 顺序敏感
  • alter nullable + 加 preTradeId + check constraint 单次迁移完成
  • server test 覆盖 review 抽屉不回归
